# ai-ops 플랫폼 방향·유지보수 전략 (논의 로그)

> **상태: ACCEPTED (방향 확정 2026-06-21). 단 구현(빌드)은 사용자 별도 승인 전까지 금지.**
> 방향 결론 = §17(최종 정리). 구축 순서 플랜은 사용자 명시 승인 후 별도 작성.

## 0. 게이트 규칙 (사용자 지시 2026-06-21)
- 이 논의는 Obsidian(이 노트) + 로컬 메모리에 **계속 기록**한다.
- **최종 결론이 난 뒤에만**, 사용자 **승인 후** 실제 작업(구현)을 시작한다.
- 그 전까지는 진단·논의·기록만. 코드 변경 금지.

## 1. 발단
사용자 질문: "ai-ops를 쓰는 것 vs Claude Code / Codex / Antigravity를 각각 개별로 쓰는 것"의 장단점과,
ai-ops가 가야 할 방향이 맞는지·계속 쓰는 게 옳은지 깊은 판단 요청.

## 2. ai-ops 현황 (실측, 2026-06-21)
- 자작 플랫폼 ~22k LOC (backend 10.4k + frontend 11.6k).
- Docker + Caddy 24/7 배포. 봇 9개를 3개 런타임에 매핑(Codex gpt-5.5 / Claude Code claude-sonnet-4-6 / Antigravity gemini-3.5-flash).
- 7개 실제 프로젝트 관리, Obsidian vault 737노트·session-log 21k줄.
- cron·학습루프·파이프라인·승인 게이트·sudo executor 보유.
- 알려진 약점: hermes WebSocket 장기 DEGRADED, run-gemini ~69h unavailable.

## 3. 1차 판단 (claude 의견)
- ai-ops를 "개발 작업 시키는 엔진"으로 쓰는 건 ROI 약함. 핸즈온 코딩은 도구 직접 사용이 더 강함.
- **가장 큰 전략 위험**: 프런티어 도구(특히 Claude Code)가 subagent·hooks·skills·background task·scheduling·MCP·plan mode 등 오케스트레이션을 빠르게 내재화 → 자작 레이어의 차별점이 릴리스마다 침식.
- ai-ops가 진짜 못 뺏기는 가치 2가지: (1) 3개 공급자가 공유하는 단일 제2의 두뇌, (2) 무인 자율 루틴 + 거버넌스(승인/sudo/failover).
- A(생산성 도구) vs B(플랫폼 구축 자체가 목표)로 분기. 중간지대(플랫폼을 생산성 도구인 척 운영하며 인프라 소방에 노력 소모)가 가장 위험.

## 4. 사용자 결정
**B 경로 채택**: 플랫폼 구축 자체를 목표로, "더 완벽하고 잘 만들고 유지보수를 잘" 하는 방향으로 진행.

## 5. 유지보수 건강도 진단 (실측, 2026-06-21)
- **테스트 사실상 없음**: backend 10.4k LOC에 테스트 3개(전부 sudo 관련). `package.json`에 `test` 스크립트 없음.
- **CI 게이트 없음**: `.github/workflows`에 webhook 트리거 1개뿐(typecheck/lint/test 관문 없음).
- **`tsconfig strict: false`**: null 안전성·implicit any 무방비. (단 현재 `tsc --noEmit` 통과.)
- **관측성 빈약**: 구조화 로그(`fastify.log`) 1회 · `console.*` 2회 · try/catch 193개 제각각.
- **god 파일**: projects.ts 685 / chat.ts 672 / learning-executor.ts 621 / stream-engine.ts 604줄.
- **frontend 소멸 리스크**: `autobots/frontend/` 전체가 부모 .gitignore에 의해 무시 + 별도 레포 + 원격 백업 없음 → `rm` 한 번에 11.6k LOC 소멸 가능. (관련: 로컬 메모리 rollback-prevention)
- 연결고리: 최근 커밋이 회귀 소방(레이스·SSE·sudo·SPA404·pnpm)으로 가득한 건 **안전망 부재**의 자연스러운 결과.

## 6. claude의 우선순위 의견 (논의용, 미확정)
방향: 기능 확장이 아니라 **표면 축소 + 코어 심화**. 순서 중요.
1. (즉시/저비용·고가치) frontend 백업·원격 확보 — 소멸 리스크 제거.
2. (안전망 1단계) 회귀 다발 경로부터 통합테스트 + CI 게이트(typecheck/lint/test).
3. (관측성) 구조화 로깅 + 헬스 일원화 → 장기 DEGRADED 즉시 알림.
4. (strict 점진 도입) 디렉터리별 단계 적용.
5. (god 파일 분해) **반드시 2번 이후**. 테스트 없이 분해 = 회귀 위험.

## 7. 쟁점 진행상황

- Q2. 최대 페인포인트 → 미답(단 §9에서 "반복 명령" 자체가 핵심 페인으로 드러남).
- Q3. 봇 self-modify 여부 → 미답(북극성에 따라 중요도 낮아짐).
- Q4(신규). 수정 북극성(§10) 동의 여부 + 봇 함대 강등 수용도 → 답변 대기.

## 9. 사용자의 진짜 목표 (2026-06-21 명확화 — 결정적)
> "봇은 가장 중요한 목표가 아니다. **반복적인 명령 없이 개발을 안정적이고 체계적으로 결과물을 완성도 있게 만드는 것**이 목표."

봇은 시도한 *수단*일 뿐. 목표 = **저반복·고신뢰 개발 시스템.**

**논리 분해 — '반복 명령'의 원인 4 + 해결책(자율 봇 함대는 어디에도 없음):**
1. 맥락 망각 → 매번 재설명 ⇒ 공유 제2의 두뇌(기둥 A).
2. 기준 미준수 → 매번 교정 ⇒ 표준·규칙 인코딩(CLAUDE.md/AGENTS.md/rules).
3. 절차 부재 → "어떻게" 재지정 ⇒ 체계적 워크플로(skills/템플릿). 씨앗: [[effective-improvement-workflow]].
4. 품질 들쭉 → 재검토·재요청 ⇒ 자동 품질 게이트(테스트/CI/리뷰 에이전트) = "완성도".
5. 잦은 파손 → 사후 소방 ⇒ 안전망+관측성 = "안정성".

**핵심 논리**: 완전 자율은 안정성·완성도를 희생(toil의 위치만 이동). 사용자는 "반복 없이"를 "안정·체계·완성도"와 한 묶음으로 요구 → 원하는 건 완전 자율이 아니라 **예측가능 반복작업의 자동화 + 판단지점에만 사람.**

## 10. 제안 북극성 (수정판, claude 제안 — 확정 대기)
> **ai-ops = 개발 운영체제(Dev OS): 공유 두뇌 + 인코딩된 표준 + 체계적 워크플로 + 자동 품질 게이트로 반복 명령을 최소화하면서 안정적·완성도 높은 결과물을 반복 생산. 판단 지점에만 사람 개입.**

- 사용자 문장 1:1 매핑: 반복없이=두뇌+표준+워크플로 / 안정=안전망+관측성 / 체계=워크플로 제도화 / 완성도=품질게이트.
- **봇의 강등**: "자율 운영자 봇 9함대 + dev-프록시 + sudo executor"(사람 대체) → 폐기/축소. "워크플로 부품·품질게이트 에이전트 + 진짜 무인 루틴"만 잔존.
- 큰 이점: 상당 부분이 **도구 네이티브 하네스(CLAUDE.md·skills·hooks·subagent·MCP)** 로 달성 가능 → 병렬 인프라 확장이 아니라 얇고 단단한 OS로 수렴 = 유지보수 승리.

## 11. 사용자 멘탈모델 검증 + 교차-벤더 통찰 (2026-06-21 — 수렴 핵심)
사용자 틀: "한 곳에 명령 → [codex/claude code/antigravity]가 역할별로 작업 → 서로 교차검증." "내 틀이 틀렸나?"

**판단: 틀리지 않음. 거의 정답. claude의 어제 '도구에서 직접' 답이 명령센터 역할을 과소평가했고 사용자가 복원.**

- **유일한 보정 — 일은 2모드:**
  - *지시형(위임형)*: 잘 정의됨 → 한 명령 디스패치 → 역할분담 → 교차검증 → 승인. **사용자 틀이 정답.**
  - *대화형(탐색형)*: 모호 → 턴마다 조향. 단일명령 없음 → 한 도구에서 라이브. 명령센터 안 맞음.
  - 실제 프로젝트 = 대화형 시작 → 지시형 전환 혼합.
- **가장 중요한 통찰 — 교차검증의 진짜 가치 = 교차-벤더:**
  - 어떤 단일 벤더 도구도 "경쟁사 모델로 내 결과를 일급 리뷰어로 독립검증"해주지 않음(자기 생태계만 최적화).
  - → 중립 교차-벤더 검증 오케스트레이션 = **도구 수렴에도 안 먹히는 유일한 해자 = ai-ops 존재 이유.**
- **단서 2개:** ① 얇게(디스패치+검증게이트+두뇌만, 페르소나 함대 X). ② 선택적(품질 중요 작업에만; 타벤더 비대화형 호출 플러밍이 가장 잘 깨짐 — run-gemini 69h 다운 증거 → 검증경로는 적게·단단하게·실패해도 안 죽게).

## 12. 확정 북극성 후보 (사용자 동의 대기)
> **ai-ops = (1) 공유 두뇌 + (2) 교차-벤더 검증을 오케스트레이션하는 얇은 명령 센터.**
> - 지시형: 한 곳 명령 → 역할 분담 → 교차검증 → 승인 (사용자 틀 그대로).
> - 대화형: 도구로 내려가 라이브 조향(두뇌 연결됨).
> - 봇 페르소나 함대·자율 dev-프록시 폐기. 검증은 얇고 선택적.

## 14. 확정 북극성 v2 (교차검증 반영 — 사용자 최종승인 대기)
> **ai-ops = (1) 공유 *검증된-아티팩트 브레인* + (2) 얇고 fail-safe한 명령 센터(spec·test 게이트 먼저 → 고위험만 선택적 교차-벤더 검증).**
> - **브레인**: 타입고정 문서만 권위(spec/ADR/runbook/test-evidence/postmortem) + 소유자·최종검증시각·만료조건. 자유메모=비권위 참고용. 갱신·큐레이션 루프 필수.
> - **검증 순서**: 명령 → 역할분담 → **spec/test 게이트** → (고위험만) 교차-벤더 검증(캐스케이드, 벤더 다운 시 graceful degrade, 절대 block 안 함) → 사람 승인.
> - **대화형**: 강한 도구 1개에서 두뇌 연결로 라이브 조향.
> - **폐기**: 9봇 페르소나 함대·자율 dev-프록시·sudo executor.
> - **측정 먼저(전제)**: SLO 정의(PR재작업률·태스크당 사람개입·승인전 defect검출율·degraded완료율) 후 모든 변경을 SLO에 대고 검증. ← 구현보다 먼저.

## 15. 인터페이스 결정: 웹/PWA vs 네이티브 앱 (2026-06-21)
**제약(사용자):** 집·회사·이동 모바일에서 같은 작업을 공통으로 이어갈 수 있어야 함.

- **핵심 통찰**: 기기 간 연속성 = 클라이언트 종류 문제가 아니라 **서버/상태 단일진실원** 문제. ai-ops는 이미 상태가 서버 SQLite(프론트에 localStorage/persist 없음 — 실측 확인) → 지금도 어느 브라우저든 동일 상태. 네이티브 앱은 연속성 개선 못 함(로컬상태 도입 시 악화).
- **현재 진단**: 이미 PWA ~80% — 반응형(sm 246·md 143·lg 34곳) + `public/manifest.json` 존재 + viewport/themeColor 설정 + 서버상태. **service worker만 부재**(푸시/오프라인 없음).
- **결정: 네이티브 앱 배제. PWA로 보강**(service worker 추가 → 설치+웹푸시+오프라인 셸). 단일 코드베이스 유지 = 북극성(저 toil)·교차검증 경고("toil 이동")와 정합. 데스크톱도 PWA 설치 가능.
- **푸시의 가치**: human-in-loop 승인 게이트(고위험 교차검증 결과·승인요청)를 폰으로 → 이동 중 판단만. "반복 명령 없이" 목표에 직결.
- **모바일 역할 구분**: 폰에서 실코딩 비현실 → 모바일=승인·모니터·디스패치·두뇌읽기. 실제 개발 이어가기는 벤더 모바일/웹(claude.ai/code 등) + 서버 호스팅 공유 두뇌. ai-ops는 명령/승인 surface(코딩 무대 아님).
- 흐름: "이동 중 폰 디스패치/승인 → 회사 도착해 도구에서 이어 코딩"이 서버상태+공유두뇌로 매끄럽게 연결.

## 16. 패스스루 검증 — "ai-ops 안에서 개발 가능한가, 웹이 문제인가" (2026-06-21)
코드 확인(stream-engine.ts:182-204,286): 현재 봇 실행 = 헤드리스 `-p`/`--print` + `acceptEdits` + allow/disallow, **메시지마다 one-shot**, history는 텍스트 재주입 = 상태없는 헤드리스 프록시.
- **"할 수 없다" 아님** — 이미 함(봇이 서버에서 도구를 레포에 대고 돌림).
- **웹은 문제 아님** — claude.ai/code도 웹·완전 인터랙티브. 웹 ≠ 열화. (claude의 어제 '웹이라 안 됨' 뉘앙스 정정.)
- **진짜 제약 = 실행 모드**(헤드리스 one-shot: 중간 조향 불가, 세션 메모리 아님, acceptEdits 통제 약).
- **두 갈래**: (A) 패스스루(진짜 인터랙티브 세션을 웹에 띄움 → ai-ops 안에서 실제 도구 그대로) = **가능·권장**. (B) 코딩 UX 재구현 = 유지보수 함정. "하면 안 됨"은 B.
- §14 보정: "대화형은 도구에서 직접" → **"대화형은 실제 도구로, 진입점은 ai-ops 패스스루 OR 도구 직접(사용자 선택)"**.

## 17. 최종 정리 (ACCEPTED, 2026-06-21)
**진짜 목표**: 반복 명령 없이 안정적·체계적·완성도 높은 개발 결과물. (봇은 수단, 목표 아님.)

**확정 북극성**: ai-ops = **단일 조종석**으로서 ① 공유 *검증된-아티팩트 두뇌* + ② *패스스루*로 연결된 실제 도구(codex/claude code/agy) + ③ *2단 검증*(싼 결정론 게이트 넓게 + 비싼 교차-벤더 LLM 검증은 고위험만 선택적) + ④ human-in-loop 승인.

**작동**:
- 지시형: 한 곳 명령 → (가벼운)역할 라우팅 → spec/test 게이트 → (고위험만) 교차-벤더 검증 → 승인.
- 대화형: ai-ops 패스스루(또는 도구 직접)로 실제 도구에서 라이브 조향, 두뇌 연결.
- 결과·결정은 두뇌에 **검증된 타입 아티팩트**로만 기록(소유자·최종검증·만료). 자유 로그 비권위.

**사용자 4단계 모델 정합**: 큰 틀 동일. 3 보정 = ⓐ두뇌=레지스트리(전체 덤프 금지, 오염방지) ⓑ역할분담=가벼운 라우팅(해자는 역할 아닌 교차-벤더 검증) ⓒ검증=2단(필요시=비싼 LLM 검증만).

**폐기**: 9봇 페르소나 함대, 자율 dev-프록시, sudo executor.

**인터페이스**: 네이티브 앱 배제, **PWA 보강**(현재 이미 ~80%). 연속성=서버상태 단일진실원(이미 보유). 모바일=승인·모니터·디스패치+벤더 모바일/웹, 실코딩은 워크스테이션.

**전제(구현 전)**: SLO 측정 먼저(PR재작업률·태스크당 사람개입·승인전 defect검출율·degraded완료율) + fail-safe 플러밍(벤더 다운 시 graceful degrade).

**근거 강도**: 웹 리서치(다수 출처) + 실제 codex·agy 교차검증 모두 "keep with changes"(폐기 신호 0). 이 검증 과정 자체가 제안 메커니즘의 실증.

**다음(게이트)**: 구축 순서 플랜 = ①SLO 정의 → ②두뇌 레지스트리화(타입/신선도/큐레이션) → ③spec/test 게이트 → ④패스스루 1개 도구부터 → ⑤선택적 교차-벤더 검증 → ⑥PWA service worker → (병행)봇 함대·sudo executor 정리. **사용자 명시 승인 후 작성·착수.**
