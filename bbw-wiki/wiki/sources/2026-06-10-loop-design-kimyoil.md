## 요약
"프롬프트를 잘 쓰는 시대"에서 "루프를 잘 설계하는 시대"로의 전환을 설명하는 영상. Boris Cherny의 "클로드가 스스로 프롬프트하게 내버려 둬라" 발언을 해석하며, AI에게 일을 맡기는 방식이 매번 명령 → 목표·기준 기반 반복 루프로 진화했음을 보여준다.

## 핵심 주장
- 프롬프트는 사라진 게 아니다 — 채팅창 명령에서 작업 감독 시스템(루프.md) 안으로 들어갔다
- 루프는 기존 설계 문서(PRD·TRD·Tasks)를 대체하지 않는다 — 그 위에 올라가는 메타 검증 레이어다
- AI에게 "완료"를 선언하기 전에 모든 기준을 스스로 확인하게 만드는 것이 루프의 역할
- 좋은 루프 = 자동 처리 기준 + 인간 호출 기준 두 가지를 명확히 구분
- 개발자의 역할 변화: 명령자 → 감독관 → **작업 시스템 설계자**

## 핵심 인사이트 원문

> Boris Cherny: "내가 클로드 코드에게 계속 프롬프트하는 게 아니라 클로드가 스스로 프롬프트하게 내버려 둔다." / "그냥 요리하게 놔둬라(Let it cook)."

> "프롬프트가 명령어였다면, 지금의 루프는 작업 감독관이다."

> "AI 개발에서 가장 위험한 문장은 '구현 완료했습니다.' 완료했다는 말은 쉽다. 문제는 증거다."

> "앞으로의 개발자는 AI에게 명령을 잘 내리는 사람이 아니라 AI가 스스로 일하고 의심하고 고치고 증거를 제출하게 만드는 사람에 가까워질 것이다."

## 루프의 3가지 기준

### 1. 필수 통과 기준 (Pass/Fail)
빌드 성공 · 타입체크 · 린트 · 테스트 · 마이그레이션 · 보안 키 노출 없음
→ 하나라도 실패하면 완료가 아님

### 2. 측정 기준 (숫자)
테스트 커버리지 · 응답 속도 · 접근성 점수 · 번들 크기 · 에러 로그 · API 실패율

### 3. 평가 기준 (점수 + 근거 필수)
아키텍처 적절성 · 코드 유지보수성 · 사용자 흐름 자연스러움 · 에러 메시지 이해도 · 작업 범위 준수
→ 점수만 쓰면 AI가 후하게 자기 평가 → 반드시 근거 + 수정 액션 포함

## 자동 처리 기준 vs 인간 호출 기준

### AI가 자동 처리해도 되는 것
린트·타입 오류 수정, 테스트 실패 로그 보고 단순 버그 수정, 누락된 테스트 추가, 문서 업데이트, 리뷰어 지적 단순 네이밍 수정

### 반드시 사람에게 물어봐야 하는 것
DB 스키마 변경, 데이터 손실 가능 마이그레이션, 인증·권한 정책 변경, 결제·보안 수정, PRD와 충돌하는 리뷰 반영, 기능 범위 확장, 테스트 통과 but 설계 의도 변경

## 운영 감시 루프 (PR 모니터링 예시)
```
15분마다 PR 상태 확인
→ CI 실패 시: 로그 분석 → 단순 오류면 직접 수정 후 재푸시
→ 리뷰 댓글: 단순 수정은 반영 / DB·권한·제품 방향 변경은 사람에게 질문
→ 모든 체크 통과 시: 머지 준비 보고서 작성
```
