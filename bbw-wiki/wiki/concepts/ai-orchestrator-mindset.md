## 정의

AI 시대에 필요한 핵심 전환: **직접 손으로 실행하는 사람**에서 **에이전트에게 위임하고 조율하는 사람**으로 변화하는 마인드셋. "AI 오케스트레이터"라고도 불림.

## 상세

### 왜 전환이 어려운가

위임은 본질적으로 어색한 행위다:
- 평생 내가 직접 하는게 편하고 빠르다고 학습해왔음
- 초반에 에이전트 훈련에 오히려 시간이 더 걸림
- 결과물을 못 믿어서 "운전대를 잡으려는" 충동이 생김
- "이 코드를 내가 안 짜면 지식을 잃어버릴 것 같다"는 불안

### 에이전트 위임이 사람 위임보다 유리한 점

| 항목 | 사람 | 에이전트 |
|------|------|---------|
| 시간 | 업무시간 제한 | 24시간 |
| 병렬 처리 | 1명 = 1작업 | 동시 다수 실행 |
| 감정 | 컨디션 영향 있음 | 없음 |
| 비용 | 급여 발생 | 토큰 비용 |

### 워크플로우 재정의 4단계

1. **Unlearn**: 기존 방식을 내려놓는다. "원래 이렇게 했으니까 AI 얹으면 되지"가 가장 흔한 실패 패턴
2. **Redefine**: 내 업무를 다시 정의한다. 일반적으로 업무의 70%는 반복(이메일·채팅·미팅 확인)
3. **Execute**: 일단 위임하고 돌린다. 처음에는 결과가 안 좋을 수 있음 — 정상
4. **Iterate**: 측정 → 프롬프트/컨텍스트 개선 → 재실행. 이 사이클을 반복할수록 워크플로우가 개선됨

### 시작하기 좋은 위임 업무의 조건

- **매일 반복하는 것**: 결과 측정이 쉽고, 실수 시 즉시 수정 가능
- **측정 가능한 것**: "30분 → 5분"처럼 숫자로 체감 가능해야 이터레이션이 된다
- 복잡하고 중요한 새 프로젝트보다 짜증나는 반복 업무부터 시작

### 생산성 재정의

- 과거: 내가 손으로 무언가를 만들고 직접 코드를 작성하는 것 = 일
- 현재: **에이전트와 대화하고 위임하고 조율하는 것 = 일**
- "글만 쓰고 하루가 끝났는데 이게 일을 한 건가?" — 이 어색함을 넘어야 함

### 코드 직접 짜기에 대한 관점 전환

> 어셈블리→C++→파이썬으로 추상화가 올라갔듯, 지금은 프로그래밍 언어에서 **자연어(한국어·영어)**로 한 단계 더 추상화됐다. 어셈블리를 안 봐도 일을 잘하듯, 코드를 직접 안 짜도 훨씬 더 큰 일을 할 수 있다.
