## 정의
AI가 어떤 태스크를 끝냈다고 선언하기 전에 스스로 확인해야 할 기준 목록을 담은 상위 감독관 문서. 기존 설계 문서(PRD·TRD·Tasks·DB 설계 등)를 대체하지 않고 **그 위에 올라가는 메타 검증 레이어**다.

```
설계 문서 계층:
PRD (무엇을 만들 것인가)
  └─ TRD (기술 구조)
  └─ Tasks (어떤 순서로)
  └─ DB 설계 / 스크린샷 / 코딩 컨벤션
       └─ loop.md (무엇을 통과해야 진짜 끝났는가) ← 이것
```

## 루프.md의 역할
> "헤이 AI. 네가 어떤 태스크를 하든 끝났다고 말하기 전에 아래 문서들을 다시 확인해라."

루프.md가 던지는 질문:
- PRD를 확인했는가?
- 유저 플로우와 맞는가?
- 스크린샷에 반영됐는가?
- DB 설계와 충돌하지 않는가?
- 코딩 컨벤션을 따랐는가?
- 테스트·타입체크·린트·빌드를 통과했는가?
- 증거를 객관적으로 제출할 수 있는가?

## 3가지 검증 기준

### 1. 필수 통과 기준 (Pass/Fail)
통과 아니면 실패 — 하나라도 실패하면 완료 선언 불가.
```
빌드 성공 · 타입체크 성공 · 린트 성공 · 테스트 성공
마이그레이션 성공 · 보안 키 노출 없음
```

### 2. 측정 기준 (숫자)
테스트 커버리지 · 응답 속도 · 접근성 점수 · 번들 크기 · API 실패율

### 3. 평가 기준 (점수 + 근거 필수)
아키텍처 · 코드 품질 · UX 흐름 · 에러 메시지 품질 · 작업 범위 준수

> ⚠️ 점수만 쓰면 AI가 자기 작업에 후한 점수를 준다. 반드시 점수 + 근거 + 수정 액션을 함께 작성하게 할 것.

예시:
```
유저플로우: 3점
근거: 일정 생성·삭제 흐름은 구현됐지만 수정 후 월간 캘린더 즉시 갱신 흐름이 미검증.
수정 액션: 일정 수정 후 캘린더 상태 갱신 테스트 추가.
```

## 운영 감시 루프 (PR 모니터링)

루프는 코드 품질 루프에 더해 **사람의 병목을 줄이는 운영 루프**로도 작동한다:

```markdown
# loop.md — PR 모니터링
- 15분마다 PR 상태 확인
- CI 실패 시: 로그 분석 → 단순 오류(린트·타입) 직접 수정 후 재푸시
- 리뷰 댓글 단순 수정 자동 반영
- DB·권한·보안·PRD 충돌 → 사람에게 질문
- 모든 체크 통과 시 → 머지 준비 보고서 작성
```

## 자동 처리 vs 인간 호출 경계

| 자동 처리 가능 | 반드시 인간 확인 |
|---|---|
| 린트·타입 오류 수정 | DB 스키마 변경 |
| 테스트 실패 단순 버그 수정 | 인증·권한 정책 변경 |
| 누락된 테스트 추가 | 결제·보안 수정 |
| 문서 업데이트 | PRD와 충돌하는 리뷰 |
| 단순 네이밍 수정 | 기능 범위 확장 |

> 경계 없이 자동화하면 "루프가 아니라 사고 제조기"가 될 수 있다.
