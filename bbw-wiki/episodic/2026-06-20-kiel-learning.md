- **ReqSpell**: 회의 메모·릴리스 노트·스프레드시트 → 구조화 요구사항 명세 자동 변환 도구. PRD 초안 가속기로 활용 가능 (ChatPRD 대안 검토 대상).

## 오늘 배운 것
- **Spec-Driven Development(SDD)**: PRD를 "구현 참고용"이 아니라 "코드를 생성하는 소스"로 취급하는 방법론. 흐름은 Spec → Plan → Tasks → Implement. GitHub Spec-Kit이 표준 도구로 부상(2026.5 기준 90k+ stars, Claude Code 포함 30+ 코딩 에이전트 연동). vibe-coding의 신뢰성 문제를 해결하는 대안으로 자리잡음.
- **SDD 스펙 ≠ 기존 PRD**: PRD는 사람이 모호함을 맥락으로 메우도록 쓰지만, SDD 스펙은 고정 스키마(user story + acceptance criteria + 제약 + constitution)로 작성. 기획자가 PRD를 "AI 입력 포맷"으로도 설계해야 하는 시대 — 자유 산문보다 구조화·모듈화 문서가 LLM 해석 품질을 크게 높임.
- **EARS notation**: 인수 조건을 EARS(Easy Approach to Requirements Syntax) 패턴으로 작성하면 모호성이 줄고 AI 코드 생성 정확도가 향상됨. 내 백로그 인수 조건 작성에 직접 적용 가능.
- **Constitution(헌법) 문서**: 기능 단위가 아닌 "교차 기능 규칙집"(품질 기준·보안 비협상 항목·아키텍처 가드레일·컴플라이언스). 기획자가 PRD와 별도로 프로젝트 전역 제약을 1개 문서로 유지하면 AI 산출물 일관성 확보.
- **AI 기반 OpenAPI 자동 생성**: 요구사항/유저스토리 → 데이터 모델 추출 → 프로덕션급 OpenAPI 명세 자동 생성(Kinde 등). 내 "API 명세서 작성" 업무를 가속하되, AI 초안은 반드시 기획자가 가지치기·검토.
- **API 명세가 에이전트 툴킷이 되는 시대**: OpenAPI에 잘 작성된 example을 넣으면 AI 에이전트의 엔드포인트 활용도가 급상승하고, MCP 표준이 API 설명을 agentic 툴킷으로 확장. 명세 작성 시 "사람+AI 소비자" 둘 다 고려해야 함.

## 위키화 후보
- **Spec-Driven Development (SDD)** — PRD를 코드 생성 소스로 삼는 방법론, Spec-Kit·constitution·EARS 구조 포함 (기존 agentic-pm 노트와 구분되는 신규 개념)
- **EARS notation** — 인수 조건 모호성 제거 구문 패턴, 백로그 작성 실무 표준

## 프로필 반영 후보 (저위험)
- 인수 조건 작성 시 EARS notation 적용 → 모호성 감소 및 AI 코드 생성 정확도 향상
- PRD는 사람용 산문 + AI 입력용 구조화 스펙 두 형태를 함께 고려해 작성 (구조화·모듈화가 LLM 해석 품질을 좌우)
